# Docker Secrets Management

This project uses Docker Compose Secrets for secure handling of sensitive data
like database passwords and encryption keys.

## Overview

Docker Secrets provide a secure way to store and access sensitive information:

- Secrets are stored as files in `./secrets/` (development) or external secret
  stores (production)
- Mounted read-only to containers at `/run/secrets/<secret_name>`
- Never exposed in environment variables, logs, or `docker inspect`
- Automatically generated by `make setup` if not present

## Configured Secrets

| Secret                  | File                                  | Mount Path                           | Used By                        |
| ----------------------- | ------------------------------------- | ------------------------------------ | ------------------------------ |
| `db_password`           | `./secrets/db_password.txt`           | `/run/secrets/db_password`           | PHP, Node, PostgreSQL, MariaDB |
| `db_root_password`      | `./secrets/db_root_password.txt`      | `/run/secrets/db_root_password`      | MariaDB only                   |
| `encryption_key`        | `./secrets/encryption_key.txt`        | `/run/secrets/encryption_key`        | PHP, Node                      |
| `backup_encryption_key` | `./secrets/backup_encryption_key.txt` | `/run/secrets/backup_encryption_key` | PHP, Node                      |

## How It Works

### 1. Secret Generation

Secrets are managed via dedicated Make commands:

| Command                         | Description                                                |
| ------------------------------- | ---------------------------------------------------------- |
| `make secrets`                  | Generate missing secrets (idempotent, safe to run anytime) |
| `make secrets-rotate-passwords` | Rotate DB passwords only (safe, preserves encryption keys) |
| `make secrets-rotate`           | Rotate ALL secrets (DANGER: breaks existing backups!)      |
| `make setup`                    | Full setup including `make secrets`                        |

```bash
# Generate missing secrets only
make secrets

# Rotate database passwords (recommended for regular rotation)
make secrets-rotate-passwords

# Rotate ALL secrets (only for compromised keys or fresh setup)
make secrets-rotate

# Full project setup (includes secrets)
make setup
```

Generated secrets:

- `db_password.txt`: 24-character alphanumeric password
- `db_root_password.txt`: 24-character alphanumeric password (MariaDB only)
- `encryption_key.txt`: 32-byte base64-encoded key (AES-256)
- `backup_encryption_key.txt`: 32-byte base64-encoded key (AES-256)

### 2. Compose Configuration

Secrets are defined in `compose.yaml`. The database services support two
mutually exclusive options:

```yaml
secrets:
  db_password:
    file: ./secrets/db_password.txt
  # ... other secrets

services:
  postgres:
    environment:
      # ─────────────────────────────────────────────────────────────────
      # PASSWORD CONFIGURATION - Choose ONE option (mutually exclusive!)
      # ─────────────────────────────────────────────────────────────────
      # Option 1: Docker Secrets (recommended, default)
      POSTGRES_PASSWORD_FILE: /run/secrets/db_password
      #
      # Option 2: Environment Variable (for external DB or legacy setups)
      #POSTGRES_PASSWORD: ${DB_PASSWORD:-secret}
      # ─────────────────────────────────────────────────────────────────
    secrets:
      - db_password

  php:
    secrets:
      - db_password
      - encryption_key
      - backup_encryption_key
    environment:
      - DB_PASSWORD_FILE=/run/secrets/db_password
      - ENCRYPTION_KEY_FILE=/run/secrets/encryption_key
      - BACKUP_ENCRYPTION_KEY_FILE=/run/secrets/backup_encryption_key
```

> **Important**: PostgreSQL and MariaDB do NOT accept both `_FILE` and direct
> password variables simultaneously. You must choose one option and comment out
> the other.

### 3. Application Code

Applications read secrets using the `_FILE` environment variable pattern:

**PHP (DatabaseConfig.php)**:

```php
// Check for _FILE variant first (Docker Secrets pattern)
$fileVar = $name . '_FILE';
$filePath = getenv($fileVar);

if ($filePath !== '' && file_exists($filePath)) {
    return trim(file_get_contents($filePath));
}

// Fall back to regular environment variable
return getenv($name) ?: $default;
```

**Node.js (database.ts)**:

```typescript
// Check for _FILE variant first (Docker Secrets pattern)
const fileVar = `${name}_FILE`;
const filePath = process.env[fileVar];

if (filePath && existsSync(filePath)) {
  return readFileSync(filePath, 'utf-8').trim();
}

// Fall back to regular environment variable
return process.env[name] ?? fallback;
```

## Security Considerations

### Development

- Secrets are stored in `./secrets/` with `chmod 600` permissions
- Directory is excluded from Git via `.gitignore`
- Auto-generated with cryptographically secure random values

### Production

For production deployments, use external secret stores:

**Kubernetes**:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: db-credentials
type: Opaque
data:
  db_password: <base64-encoded-password>
```

**HashiCorp Vault**:

```bash
vault kv put secret/myapp db_password="strong_password"
```

## Fallback Behavior

Applications support both Docker Secrets and traditional environment variables:

1. Check `{VAR}_FILE` environment variable
2. If file exists, read and return content
3. Otherwise, fall back to `{VAR}` environment variable
4. If neither exists, use default value

This allows gradual migration and external database connections that may not use
Docker Secrets.

## Disabling Docker Secrets

For external databases, legacy setups, or simpler local development, you can
switch from Docker Secrets to plain environment variables.

### Step 1: Edit `compose.yaml`

Find the database service (postgres or mariadb) and swap the password
configuration:

```yaml
# compose.yaml - postgres service
environment:
  # Comment out the _FILE option:
  #POSTGRES_PASSWORD_FILE: /run/secrets/db_password

  # Uncomment the direct variable:
  POSTGRES_PASSWORD: ${DB_PASSWORD:-secret}
```

For MariaDB, do the same for both `MARIADB_PASSWORD` and
`MARIADB_ROOT_PASSWORD`.

### Step 2: Set Password in `.env`

```bash
# .env
DB_PASSWORD=your_secure_password
DB_ROOT_PASSWORD=your_root_password  # MariaDB only
```

### Step 3: Restart Containers

```bash
make down && make up
```

> **Note**: The PHP and Node applications will automatically fall back to
> reading `DB_PASSWORD` from the environment when the secret file doesn't exist.
> No code changes required.

## Troubleshooting

### Verify Secret is Mounted

```bash
docker compose exec php cat /run/secrets/db_password
```

### Check Secret Permissions

```bash
ls -la secrets/
# Should show: -rw------- (600)
```

### Regenerate Secrets

> **Warning**: Rotating `backup_encryption_key` will make existing backups
> unreadable! Back up the old key first: `cat secrets/backup_encryption_key.txt`

```bash
# Rotate all secrets (with confirmation prompt)
make secrets-rotate
make down && make up
```

### Verify Application Can Read Secret

```bash
docker compose exec php php -r "echo file_get_contents('/run/secrets/db_password');"
```

## Best Practices

1. **Never commit secrets to Git** - Always verify `.gitignore` includes
   `/secrets/`
2. **Rotate DB passwords regularly** - Use `make secrets-rotate-passwords`
   periodically
3. **Preserve encryption keys** - Only rotate with `make secrets-rotate` if keys
   are compromised
4. **Use external secrets in production** - Kubernetes, HashiCorp Vault, or cloud providers
5. **Audit access** - Monitor who has access to secret files on the host
6. **Backup securely** - If backing up secrets, encrypt the backup separately
