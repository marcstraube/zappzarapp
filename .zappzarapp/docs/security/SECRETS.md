# Docker Secrets Management

This project uses Docker Compose Secrets for secure handling of sensitive data
like database passwords and encryption keys.

## Overview

Docker Secrets provide a secure way to store and access sensitive information:

- Secrets are stored as files in `./secrets/` (development) or external secret
  stores (production)
- Mounted read-only to containers at `/run/secrets/<secret_name>.txt`
- Infrastructure services receive per-service file secrets (each service sees
  only the secrets it reads); the application containers (php, node,
  node-backend) mount the whole `./secrets/` directory because they also consume
  optional secrets that may not exist yet (`elasticsearch_api_key.txt`,
  `mail_password.txt`)
- Files are mode 0600 with per-secret read ACLs for the consuming container uids
  (`make secrets` enforces this on every run)
- Never exposed in environment variables, logs, or `docker inspect`
- Automatically generated by `make setup` if not present; `make up` (and the
  production test / scan targets) run the same generation as a preflight, so a
  declared secret file can never be missing when Compose creates containers

## How It Works

### 1. Secret Generation

Secrets are managed via dedicated Make commands:

| Command                         | Description                                                |
| ------------------------------- | ---------------------------------------------------------- |
| `make secrets`                  | Generate missing secrets (idempotent, safe to run anytime) |
| `make secrets-rotate-passwords` | Rotate DB passwords only (safe, preserves encryption keys) |
| `make secrets-rotate`           | Rotate ALL secrets (DANGER: breaks existing backups!)      |
| `make setup`                    | Full setup including `make secrets`                        |

```bash
# Generate missing secrets only
make secrets

# Rotate database passwords (recommended for regular rotation)
make secrets-rotate-passwords

# Rotate ALL secrets (only for compromised keys or fresh setup)
make secrets-rotate

# Full project setup (includes secrets)
make setup
```

Generated secrets:

- `db_password.txt`: 24-character alphanumeric password
- `db_root_password.txt`: 24-character alphanumeric password (MariaDB only)
- `encryption_key.txt`: 32-byte base64-encoded key (AES-256)
- `backup_encryption_key.txt`: 32-byte base64-encoded key (AES-256)
- plus the credentials for the optional services (Elasticsearch bootstrap
  password, Meilisearch master key, Mercure JWT secret, pgAdmin password,
  RabbitMQ user/password, SeaweedFS S3 keys) — see the table above

### 2. Compose Configuration

Secrets are defined in `compose.yaml`. Infrastructure services list exactly the
secrets they read; the `.txt` targets keep the mount paths aligned with the
`./secrets/` directory layout. The database services support two mutually
exclusive options:

```yaml
secrets:
  db_password:
    file: ./secrets/db_password.txt
  # ... other secrets

services:
  postgres:
    environment:
      # ─────────────────────────────────────────────────────────────────
      # PASSWORD CONFIGURATION - Choose ONE option (mutually exclusive!)
      # ─────────────────────────────────────────────────────────────────
      # Option 1: Docker Secrets (recommended, default)
      POSTGRES_PASSWORD_FILE: /run/secrets/db_password.txt
      #
      # Option 2: Environment Variable (for external DB or legacy setups)
      #POSTGRES_PASSWORD: ${DB_PASSWORD}
      # ─────────────────────────────────────────────────────────────────
    secrets:
      - source: db_password
        target: db_password.txt

  php:
    volumes:
      # Application containers mount the whole directory: they consume most
      # credentials, including optional ones created after initial setup
      - ./secrets:/run/secrets:ro
    environment:
      - DB_PASSWORD_FILE=/run/secrets/db_password.txt
      - ENCRYPTION_KEY_FILE=/run/secrets/encryption_key.txt
      - BACKUP_ENCRYPTION_KEY_FILE=/run/secrets/backup_encryption_key.txt
```

> **Important**: PostgreSQL and MariaDB do NOT accept both `_FILE` and direct
> password variables simultaneously. You must choose one option and comment out
> the other.

### 3. Application Code

Applications read secrets using the `_FILE` environment variable pattern:

**PHP (DatabaseConfig.php)**:

```php
// Check for _FILE variant first (Docker Secrets pattern)
$fileVar = $name . '_FILE';
$filePath = getenv($fileVar);

if ($filePath !== '' && file_exists($filePath)) {
    return trim(file_get_contents($filePath));
}

// Fall back to regular environment variable
return getenv($name) ?: $default;
```

**Node.js (database.ts)**:

```typescript
// Check for _FILE variant first (Docker Secrets pattern)
const fileVar = `${name}_FILE`;
const filePath = process.env[fileVar];

if (filePath && existsSync(filePath)) {
  return readFileSync(filePath, 'utf-8').trim();
}

// Fall back to regular environment variable
return process.env[name] ?? fallback;
```

### 4. Compose Limitations and Hardened Containers

Docker Compose handles secrets differently from Docker Swarm, which matters for
the hardened container setup:

- **Compose ignores `mode`, `uid`, and `gid` on secrets** — these options only
  work in Docker Swarm. Under Compose, secrets are effectively bind mounts:
  ownership and permissions come from the host files. That is why the host files
  carry per-secret read ACLs for the consuming container uids.
- **`cap_drop: ALL` affects root too** — it removes all capabilities, including
  from a root entrypoint. Without `DAC_OVERRIDE`, even root cannot read files
  owned by other users.
- **`no-new-privileges` blocks `su-exec`** — privilege transitions are denied.
  Run containers as the target user directly via `user: "UID:GID"` instead.
- **A missing secret source file aborts container creation** — Compose cannot
  mount a file secret whose source does not exist. Optional secrets
  (`elasticsearch_api_key.txt`, `mail_password.txt`) therefore reach the
  application containers through their directory mount instead of per-file
  secrets.
- **Secrets flow**: PHP reads secrets directly from the `/run/secrets` bind
  mount (uid 82 read ACL). The Node development entrypoint additionally copies
  them to `/tmp/secrets/` with mode 0444, because the Node credential loader
  looks up `<name>.txt` secrets there.

## Security Considerations

### Development

- Secrets are stored in `./secrets/` (directory mode 0700) with file mode 0600
  plus per-secret read ACLs for the container uids that consume each file —
  `getfacl secrets/db_password.txt` shows who can read a secret
- Requires the `acl` package (`setfacl`); without it, `make secrets` warns and
  leaves the files owner-only, which unprivileged container users cannot read
- If you add your own secret (e.g. `mail_password.txt`), grant the application
  containers access: `chmod 600` plus
  `setfacl -b -m u:82:r,u:50000:r secrets/mail_password.txt` — `make secrets`
  re-applies the ACLs for all known secrets on every run
- Directory is excluded from Git via `.gitignore`
- Auto-generated with cryptographically secure random values

### Production

For production deployments, use external secret stores:

**Kubernetes**:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: db-credentials
type: Opaque
data:
  db_password: <base64-encoded-password>
```

**HashiCorp Vault**:

```bash
vault kv put secret/myapp db_password="strong_password"
```

## Fallback Behavior

Applications support both Docker Secrets and traditional environment variables:

1. Check `{VAR}_FILE` environment variable
2. If file exists, read and return content
3. Otherwise, fall back to `{VAR}` environment variable
4. If neither exists, use default value

This allows gradual migration and external database connections that may not use
Docker Secrets.

## Disabling Docker Secrets

For external databases, legacy setups, or simpler local development, you can
switch from Docker Secrets to plain environment variables.

### Step 1: Edit `compose.yaml`

Find the database service (postgres or mariadb) and swap the password
configuration:

```yaml
# compose.yaml - postgres service
environment:
  # Comment out the _FILE option:
  #POSTGRES_PASSWORD_FILE: /run/secrets/db_password

  # Uncomment the direct variable:
  POSTGRES_PASSWORD: ${DB_PASSWORD}
```

For MariaDB, do the same for both `MARIADB_PASSWORD` and
`MARIADB_ROOT_PASSWORD`.

### Step 2: Set Password in `.env`

```bash
# .env
DB_PASSWORD=your_secure_password
DB_ROOT_PASSWORD=your_root_password  # MariaDB only
```

### Step 3: Restart Containers

```bash
make down && make up
```

> **Note**: The PHP and Node applications will automatically fall back to
> reading `DB_PASSWORD` from the environment when the secret file doesn't exist.
> No code changes required.

## Troubleshooting

### Verify Secret is Mounted

```bash
docker compose exec php cat /run/secrets/db_password
```

### Check Secret Permissions

```bash
ls -la secrets/
# Should show: -rw------- (600)
```

### Regenerate Secrets

> **Warning**: Rotating `backup_encryption_key` will make existing backups
> unreadable! Back up the old key first: `cat secrets/backup_encryption_key.txt`

```bash
# Rotate all secrets (with confirmation prompt)
make secrets-rotate
make down && make up
```

### Verify Application Can Read Secret

```bash
docker compose exec php php -r "echo file_get_contents('/run/secrets/db_password');"
```

## Best Practices

1. **Never commit secrets to Git** - Always verify `.gitignore` includes
   `/secrets/`
2. **Rotate DB passwords regularly** - Use `make secrets-rotate-passwords`
   periodically
3. **Preserve encryption keys** - Only rotate with `make secrets-rotate` if keys
   are compromised
4. **Use external secrets in production** - Kubernetes, HashiCorp Vault, or
   cloud providers
5. **Audit access** - Monitor who has access to secret files on the host
6. **Backup securely** - If backing up secrets, encrypt the backup separately
